# Core Content

core_features:

- The local `uptime(1)` command and the `x uptime` enhancement (JSON, pretty, future provider overlay)
- A hand-curated catalog of developer-service status pages (`data/index.yml` → `data/index.tsv`)
- Self-hosted monitoring options: Uptime Kuma, Beszel, statping, Prometheus + blackbox_exporter
- Cron-style monitoring for jobs: Healthchecks.io, Cronitor, Dead Man's Snitch
- Hosted monitoring options: UptimeRobot, Better Stack, Better Uptime
- A copy-paste GitHub Actions workflow that pings a URL every 5 minutes
- An escalation pattern: GitHub Issue on probe failure, status badge from a CSV in the repo

## Key Information

highlights:

- Uptime is the same word at three scales: local box, upstream provider, your own service
- The repo's `data/index.tsv` answers "where do I check vendor X's status?" without guessing subdomains
- The catalog is regenerated by `.github/workflows/index-tsv.yml` on every push to `data/index.yml`; do not edit `index.tsv` by hand
- Uptime Kuma is the default self-hosted choice; Prometheus is the heavy option for existing-Prometheus environments
- GitHub Actions cron timing is not guaranteed — the longest documented delay is several hours — so it is a second layer, not a primary monitor
- A defense-in-depth setup pairs a hosted monitor with an independent GitHub Actions cron

## Use Cases

use_cases:

- Finding the canonical status page URL for a cloud, AI, or developer-tool provider
- Looking up which providers use the atlassian-statuspage API format (one curl gives you JSON)
- Choosing a self-hosted vs cron-style vs hosted monitoring strategy for a small site
- Adding a cheap second-layer monitor via GitHub Actions without running a server
- Triaging failure modes: "is it me, the upstream provider, or the monitor itself?"
